# DPN Emergency Correlation Contract

Phase 3B establishes `dpn-unified-emergency-network` as the server-side authority for cross-system emergency correlation.

## Canonical identifiers

Every emergency begins with one immutable root identifier:

- `eventId` — canonical root ID generated by the Unified Emergency Network.
- `medicalCallId` — optional Medical/EMS call identifier.
- `dispatchCallId` — optional canonical Dispatch call identifier.
- `incidentId` — optional Incident Command / Unified Emergency Network incident identifier.
- `mdtCaseId` — optional MDT case identifier.
- `sourceResource` — server-resolved originating FiveM resource.

The root format is `DPN-EVT-<unix>-<counter>-<entropy>`.

## Trust model

`eventId` is server-issued. A caller may submit an existing `eventId` only to continue an event already known to the canonical authority. Unknown caller-provided root IDs are discarded and replaced by a new server-issued root.

Correlation creation and linking are server-side exports. The authority intentionally does not expose a client-triggerable `RegisterNetEvent` for creating or mutating trusted correlation roots.

`sourceResource` prefers `GetInvokingResource()` so downstream resources cannot freely impersonate another server resource through payload metadata.

## Immutable links

Once a child identifier is attached to an event, attempting to replace it with a different identifier fails with `immutable-link-conflict`. This prevents one emergency from silently being rebound to a different Dispatch call, incident, Medical call, or MDT case.

## Server exports

```lua
local correlation, created = exports['dpn-unified-emergency-network']:CreateEmergencyCorrelation({
    dispatchCallId = callId
})

local ok, updated = exports['dpn-unified-emergency-network']:LinkEmergencyCorrelation(
    correlation.eventId,
    'incidentId',
    incidentId
)

local valid, authoritative = exports['dpn-unified-emergency-network']:ValidateEmergencyCorrelation(correlation)

local current = exports['dpn-unified-emergency-network']:GetEmergencyCorrelation(correlation.eventId)
```

## Phase 3B integration sequence

1. Establish the canonical authority and CI protection.
2. Route new canonical Dispatch calls through `CreateEmergencyCorrelation`.
3. Propagate `eventId` into Officer Safety, Incident Command, Medical Dispatch, EMS, and Unified Emergency Network incident payloads.
4. Link Dispatch and Incident IDs rather than creating duplicate calls.
5. Carry the same correlation into MDT case creation and report synchronization.
6. Add persistence/restart recovery for active correlations after runtime integration is stable.

## Compatibility

Legacy callers do not need to supply a correlation payload immediately. New integrations can create one at their first authoritative server boundary and pass it forward. This allows Phase 3B migration without breaking older event payloads while later phases remove duplicate dispatch ownership and complete MDT synchronization.
