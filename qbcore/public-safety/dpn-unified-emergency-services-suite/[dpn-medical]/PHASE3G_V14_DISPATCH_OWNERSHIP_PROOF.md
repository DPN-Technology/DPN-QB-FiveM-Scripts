# Phase 3G — v14 Medical Dispatch Ownership Proof

Baseline: `main` at `76d3ae559d48f17ed1665fc2d75e34efa4076210`.

## Purpose

This proof records the fresh Phase 3G audit of `dpn-medical-dispatch/server/v14.lua` before any attempt to apply the v9–v13 compatibility-routing pattern to v14.

The result is intentionally conservative: **v14 does not currently require the same compatibility-router rewrite as v9–v13.** The v14 layer emits local medical events and does not directly select or broadcast into an external dispatch namespace.

## Audited v14 surfaces

`server/v14.lua` currently exposes these dispatch-facing workflow operations:

- `CreateTraumaCodeV14`
- `RecommendTraumaAssetsV14`
- `EscalateTraumaIncidentV14`
- `GetV14DispatchBoard`
- `GetV14Cases`

The two workflow operations that emit events are:

- `CreateTraumaCodeV14` → `TriggerEvent('dpn-medical:v14:trauma_code', item)`
- `EscalateTraumaIncidentV14` → `TriggerEvent('dpn-medical:v14:incident_escalation', item)`

These are local `dpn-medical:v14:*` events. The v14 source does **not** directly emit `dpn-dispatch-system`, `dpn-dispatch`, or another external dispatch-resource namespace.

## Ownership conclusion

For Phase 3G ownership purposes:

1. v14 owns its trauma-command case construction, persistence, board state, risk/tier/destination/resource-demand data, and local medical event publication.
2. v14 does not currently own external dispatch-resource selection.
3. The shared `DPNMedicalDispatchCompatBridge` should not be inserted into v14 merely for symmetry with historical layers when no external compatibility fan-out exists.
4. Any future consumer of `dpn-medical:v14:trauma_code` or `dpn-medical:v14:incident_escalation` that creates an external dispatch call should remain the place where external dispatch ownership is evaluated.
5. A future runtime change is warranted only if fresh repository evidence shows v14 directly selecting multiple external dispatch targets or duplicate external calls being generated by its local-event consumers.

## Safety / no-change decision

No v14 runtime code is changed by this proof. This avoids unnecessary re-routing, preserves all unique v14 behavior, and prevents a symmetry-driven change from introducing duplicate calls or compatibility regressions.

The following remain unchanged:

- v14 exports and event names
- persistence and database writes
- case/board state
- trauma scoring and recommendations
- payload structure
- permissions and authorization boundaries
- historical compatibility behavior
- dispatch bridge behavior
- CI requirements

## Integration relationship to open Phase 3G work

This proof is independent of the open v9–v12 routing PRs and the shared compatibility-fallback ownership preparation. It does not modify the same runtime files or Quality Gate workflow, so it can be reviewed without stacking additional runtime or CI rebase debt.

Before any later Phase 3G v14 runtime patch is proposed, re-run this audit from then-current `main` and require concrete evidence of an external ownership collision. If that evidence does not exist, retain the no-change decision.
