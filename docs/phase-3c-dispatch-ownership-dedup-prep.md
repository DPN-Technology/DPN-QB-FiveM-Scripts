# Phase 3C — Dispatch Ownership & Deduplication Preparation

## Purpose

This document prepares the Phase 3C implementation without changing runtime behavior or creating dependency on the still-draft Phase 3B branch. It is based directly on secured `main` at `2c642c267e250ebd8c9028572cc06c26559c7893`.

Phase 3C will establish one canonical dispatch-call ownership path while preserving existing resource compatibility and unique gameplay behavior. No legacy path should be deleted until its behavior is mapped, callers are migrated, and regression coverage proves parity.

## Current ownership surfaces observed on `main`

The repository currently exposes or consumes dispatch-call creation through several independent surfaces:

- `core/dpn-mdt/server/main.lua` contains its own `createDispatchCall` persistence path into MDT dispatch storage.
- `core/dpn-mdt` publicly documents a `CreateDispatchCall(callData)` server export.
- `core/dpn-mdt/integration_examples/dpn-dispatch.lua` forwards dispatch calls into MDT through that export.
- `core/dpn-mdt/integration_examples/unified_emergency_network.lua` independently forwards UEN incidents into MDT dispatch-call creation.
- `[dpn-lawenforcement]/dpn-officer-safety/server/main.lua` has a local dispatch-call adapter that calls the configured dispatch integration.
- `[dpn-lawenforcement]/dpn-le-core/server/main.lua` has another local `createDispatchCall` adapter.
- `[dpn-lawenforcement]/dpn-digital-dispatch` exposes its own `CreateDispatchCall` API.
- `[dpn-medical]/dpn-medical-dispatch/shared/config.lua` probes multiple dispatch resources and multiple call-creation export names in `first_success` mode, with event fallback behavior configurable.
- `core/dpn-unified-emergency-network/server/dispatch.lua` owns incident fan-out to eligible units.
- `core/dpn-dispatch` is a separate full dispatch resource with its own client/server/UI lifecycle.

These surfaces are not automatically defects: some are adapters, some are persistence sinks, and some are user-facing dispatch systems. Phase 3C must distinguish ownership from integration before consolidation.

## Phase 3C invariants

1. **One authoritative creation decision per emergency dispatch call.** A single logical emergency must not be independently materialized as multiple canonical dispatch calls.
2. **Correlation survives every adapter.** Once Phase 3B is merged, `eventId` and `dispatchCallId` must be propagated rather than regenerated by downstream resources.
3. **Persistence sinks do not become identity authorities.** MDT may persist a dispatch record, but must not silently mint a second canonical emergency identity for an already-correlated call.
4. **Adapters are idempotent.** Re-delivery of the same correlated call must update/reuse the same canonical record or no-op safely.
5. **Server authority only.** Client-provided call IDs, event IDs, source-resource identities, or dedup keys must not be trusted as authoritative without server-side validation.
6. **No fan-out multiplication.** Export success plus event fallback must never emit the same logical call twice.
7. **Compatibility is preserved.** Existing public exports/events may remain as compatibility facades while routing into the canonical authority.
8. **No unique gameplay functionality is deleted.** UI, unit assignment, notifications, escalation, agency routing, MDT persistence, and medical/law-enforcement-specific behavior remain intact unless an exact duplicate path is proven and safely retired later.

## Implementation sequence after Phase 3B lands

### 1. Build an ownership map

For every dispatch-producing resource, classify each path as one of:

- canonical creator,
- compatibility adapter,
- persistence sink,
- notification/fan-out consumer,
- UI/read model,
- specialized producer.

Record export/event names, input schema, generated IDs, persistence behavior, and downstream fan-out.

### 2. Introduce canonical dedup keying

Use the Phase 3B emergency correlation contract as the primary identity. For correlated emergencies, the root `eventId` plus immutable `dispatchCallId` linkage should be the first-choice dedup authority. Any fallback dedup key for uncorrelated legacy callers must be server-generated, bounded in time, and explicitly temporary.

### 3. Route compatibility APIs through one authority

Existing APIs such as `CreateDispatchCall`, `CreateCall`, and `CreateIncident` should remain callable where compatibility requires them, but their implementation should converge on one server-owned dispatch creation function. Callers should receive the canonical dispatch identity rather than generate their own.

### 4. Make MDT ingestion idempotent

`dpn-mdt` dispatch ingestion should upsert/reuse based on the canonical correlated identity rather than create a second record for repeated delivery. MDT remains a durable consumer/read model unless an explicit architecture decision later makes it the dispatch authority.

### 5. Eliminate export-plus-event duplicates

Medical and other integration adapters that probe multiple exports/events must stop after the first confirmed canonical acceptance. Fallback events should run only when no canonical export accepted the call.

### 6. Add regression enforcement

Phase 3C CI should verify at minimum:

- one canonical dispatch ownership implementation,
- no client-triggerable path can mint authoritative dispatch correlation IDs,
- correlated dispatch IDs are propagated rather than regenerated,
- duplicate delivery of the same canonical correlation is idempotent,
- `first_success` adapters do not also emit fallback events after success,
- MDT ingestion does not create duplicate canonical records for the same correlation,
- all pre-existing Quality Gate checks remain present, including medical registry and MIB loadout authorization guards.

## Non-goals for this preparation branch

- No runtime dispatch behavior changes.
- No deletion or disabling of dispatch resources.
- No database migration.
- No Phase 3B code copy or cherry-pick.
- No MDT ownership change.
- No branch-protection, workflow-policy, release, visibility, license, or ownership changes.

This preparation branch can therefore remain independent of Phase 3B and be discarded or refreshed cleanly after Phase 3B merges without creating rebase debt.
