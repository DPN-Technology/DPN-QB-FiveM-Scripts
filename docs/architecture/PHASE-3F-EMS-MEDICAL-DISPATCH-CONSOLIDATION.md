# Phase 3F — EMS / Medical Dispatch Consolidation Invariants

Status: design/preparation only. This document is intentionally based on current `main` and does not depend on unmerged Phase 3B–3E runtime changes.

## Objective

Consolidate EMS/medical-dispatch ownership without deleting unique functionality, weakening compatibility, or introducing multiple authoritative call records for the same emergency.

The target state is one server-authoritative medical-dispatch lifecycle with compatibility adapters for existing event/export surfaces and preserved advanced decision-support modules.

## Current-state observations

The medical dispatch resource contains a base server implementation plus multiple version-specific server modules. Existing modules provide unique functionality including duplicate detection, readiness/ETA-based unit ranking, predictive medical call creation, regional incident creation, continuum-asset recommendations, and integration bridges into other dispatch resources.

Because these modules provide distinct behavior, Phase 3F MUST NOT be implemented as bulk file removal or a version-folder purge. Consolidation must first identify the canonical state owner and then adapt unique capabilities onto that owner.

## Canonical ownership

1. Exactly one server-side component owns creation and lifecycle mutation of a medical dispatch call.
2. A call has one canonical immutable identity.
3. Phase 3B emergency correlation identifiers, once available, are carried through medical dispatch and MUST NOT be regenerated by downstream adapters.
4. No client-provided identifier is trusted as authoritative without server validation.
5. Compatibility bridges may translate or mirror state, but they MUST NOT create a second authoritative lifecycle.
6. Restart recovery must not convert replayed state into new calls.

## Creation and deduplication

All call-producing paths must converge on one internal creation service.

Required behavior:

- normalize location, caller, patient, priority, incident type, and correlation metadata;
- derive a deterministic or server-maintained idempotency key for equivalent submissions;
- reject or attach duplicate submissions according to policy rather than silently creating parallel calls;
- preserve the strongest known priority/severity when duplicate inputs disagree;
- retain source provenance for audit without treating source resource names as identity;
- prevent event/export fallback fan-out from producing multiple calls.

Legacy events and exports remain callable during migration, but they should become thin adapters around the canonical creation service.

## State lifecycle

The canonical medical call lifecycle must define explicit transitions such as:

`created -> acknowledged -> assigned -> responding -> on_scene -> transporting -> transferred -> closed`

Additional clinically meaningful states may be retained, but transitions must be validated server-side.

Rules:

- state changes are monotonic unless an explicitly permitted recovery transition exists;
- stale updates cannot overwrite newer revisions;
- unit assignment is idempotent;
- a unit cannot be unintentionally assigned twice through separate adapters;
- close/cancel operations require an auditable reason where appropriate;
- replayed events after reconnect/restart cannot reopen a closed call without an explicit authorized transition.

## EMS unit ownership

One component must own the authoritative EMS-unit assignment relation for each call.

Dispatch recommendation modules may score or recommend units, but recommendations are not assignments until accepted by the authoritative assignment service.

Unit availability, readiness, ALS/BLS capability, ETA, workload, specialty assets, and regional coverage may remain inputs into scoring. Existing advanced ranking/recommendation functionality should be preserved as pluggable strategy modules.

## Medical Core boundary

Phase 3E Medical Core and Phase 3F medical dispatch must have a strict ownership boundary:

- Medical Core owns authoritative patient/clinical state.
- Medical Dispatch owns authoritative emergency-call and EMS-response state.
- Dispatch may read a bounded clinical summary needed for prioritization.
- Dispatch must not directly mutate clinical state outside approved Medical Core APIs.
- Medical Core may emit severity/status signals, but those signals must not directly create duplicate dispatch calls when a correlated call already exists.

## General dispatch boundary

Phase 3C is expected to establish general dispatch ownership/deduplication. Phase 3F must integrate with that model rather than compete with it.

Requirements:

- one emergency may have both general-dispatch and medical-specific views without becoming two unrelated incidents;
- medical calls link to the canonical emergency/dispatch identity when available;
- compatibility bridges to `dpn-dispatch-system`, `dpn-dispatch`, or other legacy surfaces must be delivery adapters, not independent creators;
- loop suppression is mandatory for bidirectional integrations;
- one inbound call must not return through a bridge and create itself again.

## MDT boundary

When Phase 3D MDT integration is active:

- MDT ingestion must consume the canonical dispatch identity;
- MDT case creation must be idempotent;
- MDT acknowledgements/status updates cannot independently mutate medical-call identity;
- medical details exposed to MDT should be limited to operationally required information;
- correlation links are immutable once established except through an explicit audited repair process.

## Preserve unique functionality

The following categories must be preserved unless a later focused change proves them obsolete and receives explicit approval:

- duplicate-call detection;
- predictive medical dispatch;
- regional/mass-casualty incident support;
- readiness/ETA/capability scoring;
- specialty/continuum asset recommendations;
- escalation logic;
- clinically informed dispatch priority;
- compatibility events and exports used by existing resources;
- operational telemetry and audit data.

Consolidation means sharing canonical state and APIs, not deleting features simply because they originated in different version modules.

## Security invariants

1. All authoritative create/update/assign/close operations execute server-side.
2. Client payloads are treated as requests, not authority.
3. Job/role/grade permissions are resolved from server state.
4. Target player/unit identifiers are validated before mutation.
5. Routing/bucket/world context must be considered where relevant.
6. High-impact administrative or clinical overrides require explicit authorization and audit logging.
7. No compatibility adapter may bypass the canonical authorization path.

## Performance invariants

- no permanent zero-delay polling loops;
- no unbounded in-memory call or fingerprint tables;
- deduplication indexes require bounded retention/cleanup;
- expensive scoring runs only when inputs materially change or on bounded intervals;
- bridge delivery uses bounded retries/backoff rather than hot retry loops;
- persisted/recovered state loads in bounded batches where practical;
- telemetry cannot block the authoritative dispatch path.

## Migration approach

Implement in focused stages after prerequisite phases land:

1. inventory every medical-call creation/update surface;
2. define canonical internal call schema and revision semantics;
3. introduce canonical creation/get/update/assign APIs behind existing behavior;
4. route base `server/main.lua` through the canonical service;
5. adapt version-specific creation paths to the same service;
6. adapt general-dispatch bridges with loop suppression and idempotency;
7. integrate Phase 3B correlation IDs when available;
8. integrate Phase 3C ownership/dedup rules;
9. integrate Phase 3D MDT linkage;
10. integrate Phase 3E Medical Core patient-state boundary;
11. retain compatibility aliases until repository-wide usage proves removal safe.

## CI requirements before runtime consolidation may merge

Add regression checks that fail when:

- more than one authoritative medical call store/creator is introduced;
- a legacy adapter bypasses the canonical creation path;
- client-controlled IDs become authoritative without validation;
- bridge fan-out can emit more than one canonical call for one inbound request;
- immutable correlation identifiers are rebound;
- unit assignment lacks idempotency protection;
- stale revisions can overwrite newer call state;
- existing unique version-specific exports disappear without an explicit compatibility mapping;
- Medical Core state is mutated directly from dispatch outside approved APIs;
- required security/performance checks are removed from the DPN Quality Gate.

## Exit criteria

Phase 3F runtime work is complete only when:

- one authoritative medical-dispatch lifecycle exists;
- all supported legacy creation paths converge on it;
- duplicate submissions resolve idempotently;
- unique medical-dispatch features remain available;
- general dispatch, MDT, Medical Core, and emergency-correlation boundaries are explicit;
- migration is covered by automated regression checks;
- the exact PR head is green on all required repository workflows.

No runtime behavior is changed by this preparation document.
