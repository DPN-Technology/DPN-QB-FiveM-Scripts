# About This Repository

Welcome to **DPN QB FiveM Scripts**, the official GitHub repository for free FiveM resources created and released by **DPN Technology** and **CEO Diesel**.

This repository exists to provide FiveM server owners, developers, hobbyists, community administrators, and new scripters with useful resources they can actually work with.

The goal is not to lock everything behind encryption, subscriptions, or paid downloads.

The goal is to release useful scripts that people can:

- Install on their FiveM servers.
- Study to learn how FiveM resources work.
- Configure for their own communities.
- Modify to match their server style.
- Expand with new features.
- Integrate with other resources.
- Improve for performance or usability.
- Fork for private development.
- Use as a base for their own server-specific systems.
- Contribute improvements back to the community.

Most resources in this repository will be built for one of two environments:

- **QBCore**
- **Standalone FiveM**

Some scripts may support both.

Each script should clearly identify its framework requirements, dependencies, configuration options, installation instructions, and any special setup requirements.

# What You Can Expect

DPN Technology aims for resources in this repository to follow several core standards.

## 1. Editable Source

Unless specifically stated otherwise, scripts are released with readable source code so server owners can customize them.

## 2. Clear Configuration

Where practical, configurable values should be placed in an obvious configuration file instead of being buried throughout the code.

Every script should identify whether it is:

| Type | Meaning |
|---|---|

Resources should include enough documentation for a server owner to understand:

- What the resource does.
- What it requires.
- Where to install it.
- How to configure it.
- How to start it.
- Whether SQL is required.

- How to troubleshoot common issues.

You can use and edit the resources.

# Quick Installation

For most resources, installation follows this general process.

## Step 1 — Download the Resource

Clone the repository:

~~~bash
git clone https://github.com/directordiesel/DPN-QB-FiveM-Scripts.git
~~~

Or download the repository ZIP from GitHub.

## Step 2 — Locate the Script

Find the resource you want to use.

Do not automatically install the entire repository as one FiveM resource.

Individual scripts should normally be copied into your server's resources directory.

Example:

~~~text
resources/
└── [dpn]/
    └── dpn-example-resource/
~~~

## Step 3 — Read the Resource README

Before starting the script, check for:

- Required dependencies.
- SQL files.
- Config options.
- QBCore requirements.
- Optional integrations.
- Permission settings.
- Required items.
- Required jobs.
- Required exports.

## Step 4 — Configure the Script

Edit the configuration files for your server.

Never blindly copy configuration values from another server.

## Step 5 — Add the Resource to server.cfg

Example:

~~~cfg
ensure dpn-example-resource
~~~

## Step 6 — Restart or Refresh

You may use:

~~~text
refresh
ensure dpn-example-resource
~~~

during development, but production servers should generally restart resources carefully to avoid breaking active player sessions.

## Step 7 — Test

Test before moving the resource into production.

# QBCore Installation

For a QBCore script, the general process is:

1. Confirm QBCore is installed and working.
2. Confirm the script supports your QBCore version.
3. Install any listed dependencies.
4. Add required items, jobs, or shared definitions.
5. Import SQL if required.
6. Configure the resource.
7. Add it to your start order.
8. Restart the server.
9. Watch both server and client consoles for errors.
10. Test all important features using a test character.

A common start order may look like:

~~~cfg
ensure oxmysql
ensure qb-core
ensure qb-target
ensure qb-inventory

ensure dpn-example-resource
~~~

Your actual dependencies may differ.

Do not assume the example above applies to every script.

# Standalone Installation

Standalone resources do not require QBCore, but they may still depend on other resources.

Typical installation:

~~~cfg
ensure dpn-standalone-example
~~~

If ACE permissions are used, you may also need entries similar to:

~~~cfg
add_ace group.admin dpn.admin allow
~~~

Always use the permission names defined by the script.

# Database Resources

Some scripts may require database tables or modifications.

If a resource contains an SQL file:

1. Back up your database.
2. Review the SQL file.
3. Import it into the correct database.
4. Confirm the table was created successfully.
5. Restart the resource.
6. Check for migration errors.

Never run unknown SQL against a production database without reviewing it.

## Recommended Backup

Before major changes:

~~~text
1. Stop the server.
2. Back up the database.
3. Back up the resource.
4. Apply the update.
5. Start a test environment.
6. Validate functionality.
7. Move to production.
~~~

# Updating Scripts

When a DPN script receives an update, do not immediately overwrite your customized version.

Recommended update process:

1. Back up your current copy.
2. Review the changelog or commit history.
3. Compare your modified files.
4. Copy new changes carefully.
5. Merge configuration changes.
6. Review database changes.
7. Test on a staging server.
8. Deploy to production only after testing.

If you heavily modify a DPN script, consider using Git so you can merge upstream changes properly.

Example:

~~~bash
git remote add upstream https://github.com/directordiesel/DPN-QB-FiveM-Scripts.git
git fetch upstream
~~~

# Performance Expectations

FiveM performance matters.

Resources should aim to avoid unnecessary client or server load.

Good practices include:

- Avoiding constant 0ms loops unless truly necessary.
- Using events instead of polling where possible.
- Increasing wait intervals when players are not near an interaction.
- Caching values that do not need constant recalculation.
- Validating server-side data efficiently.
- Avoiding unnecessary database queries.
- Indexing frequently queried database columns when appropriate.
- Avoiding excessive network event spam.
- Avoiding unnecessarily large NUI messages.
- Cleaning up created entities.
- Removing event handlers when appropriate.
- Avoiding duplicate threads.
- Avoiding duplicate commands.
- Avoiding repeated framework lookups when caching is safe.

## Performance Testing

Use FiveM tools such as the resource monitor and profiler when diagnosing performance.

Do not judge performance solely by file size.

A 20 KB resource can perform worse than a 2 MB resource if its logic is inefficient.

# Security Guidelines

FiveM resources should never trust the client with authority it should not have.

## Server-Side Validation

Sensitive operations should be validated on the server.

Examples:

- Giving money.
- Removing money.
- Giving items.
- Removing items.
- Setting jobs.
- Setting permissions.
- Spawning protected rewards.
- Completing jobs.
- Paying job rewards.
- Accessing privileged actions.
- Saving sensitive data.
- Administrative actions.

A client event should not be able to simply tell the server:

~~~text
"Give me $1,000,000"
~~~

without validation.

## Validate

Where relevant, validate:

- Player source.
- Player identity.
- Player job.
- Player grade.
- Player permissions.
- Player location.
- Item ownership.
- Required state.
- Cooldowns.
- Submitted values.
- Database state.
- Entity existence.
- Ownership.
- Allowed ranges.

## Never Trust NUI Input

NUI data is client-controlled.

Validate important actions server-side.

## Do Not Hide Bad Security Behind Obfuscation

Obfuscating code is not a replacement for secure architecture.

Security should come from proper validation, not from assuming players cannot read or trigger events.

# Bug Reports

When reporting a bug, provide enough information to reproduce the problem.

A good bug report includes:

- Resource name.
- Resource version or commit.
- QBCore version if applicable.
- FiveM artifact version.
- Dependencies.
- What you expected.
- What happened instead.
- Steps to reproduce.
- Client console errors.
- Server console errors.
- Relevant configuration.
- Whether the resource was modified.
- Whether the issue also occurs on an unmodified copy.

~~~text
script broke fix pls

Resource: dpn-example
Framework: QBCore
Issue: Command opens UI but submit button does nothing.
Steps:

Server console: no error
Client F8: attempt to index nil value on client.lua:84
Modified resource: No
~~~

# Coding Standards

Not every contribution must follow identical formatting, but consistency is encouraged.

## Naming

Prefer descriptive names.

Better:

~~~lua
local playerJob = PlayerData.job
local interactionDistance = 2.0
~~~

Less clear:

~~~lua
local x = PlayerData.job
local a = 2.0
~~~

## Events

Use consistent names.

Example:

~~~text
dpn-resource:client:openMenu
dpn-resource:server:saveData
~~~

## Configuration

Do not scatter configurable values throughout multiple files unless necessary.

## Logging

Debug output should generally be controlled by a configuration option.

Example:

~~~lua
if Config.Debug then
    print("[DPN] Debug message")
end
~~~

## Comments

Comments should explain why complex logic exists, not simply repeat the code.

## Server Authority

Rewards and protected state changes should be controlled server-side.

Resources may use semantic-style versions such as:

~~~text

2.0.0
~~~

A general interpretation:

| Version Change | Example | Meaning |
|---|---|---|
| Major | 1.0.0 → 2.0.0 | Large changes or breaking compatibility |
| Minor | 1.0.0 → 1.1.0 | New features, normally backward-compatible |
| Patch | 1.1.0 → 1.1.1 | Bug fixes or small changes |

Not every legacy resource will necessarily follow strict semantic versioning.
